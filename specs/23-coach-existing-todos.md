# Spec 23: The coach adds to-dos to events already in the calendar
Asked for by the owner on 13 Nov 2026. He wrote to the coach, about an event already in his calendar: "For that one I also want the to-dos: do the investment exercises, and watch the investment lecture." The coach answered that it cannot add to-dos to existing events. He wants that to work. Plan: `docs/ontology.md` (`draft_plan`, `accept_draft`, `undo_draft`, `edit_draft`, R1, R4, R11, R22, R23, R40, A23; changes of 13 Nov 2026 on this branch). Branch: `23-coach-existing-todos`, built on `22-draft-drag` (spec 22).

## Why
Spec 21 lets the coach write to-dos only into the new events of a draft. Often the block is already in the calendar ("Lernblock" tomorrow afternoon) and the person only wants to say what to do in it. Opening the event and typing each to-do by hand is what the coach should save him, under the same rule as before: Claude only proposes, our server checks, nothing changes before the person applies the draft, and an applied draft can be undone.

## What
- [x] A fourth kind of thing in a draft: to-dos for an event already in the calendar, named by its reference like a move or delete, with 1 to 20 titles, each 1 to 100 characters after trimming, in the person's words. Applying adds them at the end of that event's list, not done. Still only a proposal: nothing changes before "Apply changes".
- [x] Which events (decision 2): the user's own events that are not from Outlook (R11, R40) and have not ended before today; unlike moving, also an event of a series (the to-dos go to that one event), an all-day event and an event that has started. The data block gives each event a second flag for this next to `changeable` (`"canAddTodos": false`, sent only when false) and its number of to-dos (`todoCount`, sent only when above 0); never their titles.
- [x] Together with other changes (decision 3): an event may be moved and get to-dos in one draft; an event the draft deletes gets nothing else; each event at most once per kind.
- [x] Checks (R23, extended; `src/lib/chat/checks.ts`, pure): the reference exists and the event takes to-dos; the count and length of the titles; the event's to-dos now plus the new ones at most 20. One failed check rejects the whole answer (R1). The draft's limit of 30 counts each "to-dos for an event" as one.
- [x] `accept_draft` applies them in the same transaction as the rest of the draft. The event must still be there, be the user's, not be from Outlook and have room (it need not be unchanged: editing its time in between does not matter); otherwise "This draft is out of date. Ask again". The database writes the to-dos and keeps their ids in the undo data itself, so the undo data cannot be forged. The event's `updated_at` stays (R40).
- [x] `undo_draft` removes exactly the to-dos the draft added that still exist (ticked or renamed ones too) and closes the gaps in the list. They never block undo, nor does an event deleted since; the other rules of undo stay.
- [x] `edit_draft` (dragging, spec 22): not for this kind; the draft's other blocks can still be dragged, and the checks run on the whole draft with them.
- [x] What Claude is told (`prompt.ts`): it may add to-dos to an existing event when the person asks for it, naming the event by its reference; the to-dos in the person's own words, never invented; if the event takes none or its list would get too long, say so in words. The answer format has the list `addTodos` of `{ref, todos}`. Earlier drafts in the history carry it in words (`addedTodos`: the event's title and the to-dos).
- [x] The screen (`DraftCard.tsx`, `day-sketch.ts`): in the draft's day column the event is drawn as already in the calendar, pale, with a small mark "+2 to-dos" (an all-day event among the all-day chips, on its first day); under the column the list "To-dos for 'Lernblock'" with the new titles; the screen-reader list says "…, already in the calendar, 2 to-dos added". The event's day is shown also when the draft has nothing else on it. The button reads "Apply changes"; after applying and after undo the card behaves as for the other kinds. "What is sent?" says that each event's number of to-dos is sent, never their titles.
- [x] Database (`supabase/migrations/20261127000000_coach_existing_todos.sql`, additive): the column `app.draft_plans.added_todos` (empty list by default); the user's role may add it with the draft and never change it (insert right on that one column only, no update right, and a trigger refuses any change); the draft's "1 to 30 things" counts it; the security definer function `app.chat_apply_draft_todos` does everything `app.chat_apply_draft` did and also writes these to-dos under the event's row lock. `app.chat_accept_draft` (19) and `app.chat_apply_draft` (20 to 22) refuse a draft with such to-dos and otherwise work as before; `app.chat_undo_draft` also removes them. `main`, `19-coach`, `20-coach-changes`, `21-event-todos` and `22-draft-drag` work unchanged against it.

## Out of scope
The coach ticking, renaming or removing to-dos; to-dos for Outlook events (R11); dragging to-dos or moving them between events; a to-do's own due date; undo of a single to-do.
