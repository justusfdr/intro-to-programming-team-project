# Spec 43: The coach plans with a goal's routine
Decided in the team meeting of 16 Nov 2026: a goal is set up through guided questions and "the coach then knows the facts about the gym, the running or the studying" and plans the day around the calendar and those facts; the team confirms with the merge. Step 3 of 3: spec 41 saved and checked a goal's routine, spec 42 asked for it in six questions. Plan: `docs/ontology.md` (R22, R23, R44's last sentence, the new R45, `accept_draft`, section 7, A27; changes of 16 Nov 2026 on this branch). Branch: `43-coach-goal-routine`, built on `42-goal-setup`.

## Why
A goal now knows how long a session is, when in the day it suits, the weekdays it never happens on and where it is done. Until now the coach saw only the goal's title and rules, so "plan my week" put the gym on a Friday the person never goes, at a random hour, with no time to get there. The coach should plan the sessions that are still missing, where they fit, and our server should make sure it never plans on a day the person ruled out. As always: Claude only proposes, our server checks, nothing changes before the person accepts, and accepting can be undone.

## What
- [x] What Claude receives (R22, extended; `src/lib/chat/input.ts`): a goal that has a routine also carries, each key only when it has a value, `category` (and `categoryOther`), `sessionMinutes`, `dayPart`, `never` (weekday names), `neverDates` (those weekdays as dates from today to `lastDayForProposals`), `away: true` (a place that is not a web link) and `weeks` (the current and the next week with the sessions `left`). The place itself is never sent: no address, no name. A goal without a routine is sent exactly as before, byte for byte.
- [x] The sessions left (R45; `src/lib/chat/goal-weeks.ts`, pure): per `count` rule the target minus the done events of the week minus the events still planned in it from the start of today on (with `min_minutes` only those long enough); per `hours` rule the target's minutes minus the minutes done and planned, divided by the session length (60 without one), rounded up; the goal's value is the largest, never below 0; no week after the deadline. Done events come from R31's read; planned ones from the coach's calendar read, which now also reads each event's status (kept on the server).
- [x] What Claude is told (`prompt.ts`): a new section "Planning for the person's goals": the keys and the hours of the parts of the day; plan the sessions left on the days asked for, one session per goal and day at most, as long as `sessionMinutes`, with the goal's title and id; in the goal's part of the day when there is room, otherwise say so; never on a never date (and say that the person can change this in the goal); 30 minutes free before and after a session away from home; say what did not fit; no goal sessions for a question or one specific request; a goal without `weeks` gets only what is asked for. The answer format is unchanged.
- [x] Checks (R23, extended; `checks.ts`): a new event that names a goal must not start on a weekday the goal is never done on (the start's weekday in the person's time zone). It runs on the answer (`send_message`), again on `accept_draft` against the goal as it is then ("This draft is out of date. Ask again", nothing changed) and on `edit_draft` (dragging). Moves, events without a goal and the person's own events are not checked. The part of the day and the 30 minutes are wishes, not checked. The checks' context has one more optional field, so every earlier caller is unchanged.
- [x] An accepted session takes the goal's place (R45): every event the draft creates for a goal that has a place gets it as its location, in the accept's transaction. Moved events keep their location; undo removes the created events as before.
- [x] Two ways into the coach: "Let the coach plan it into my week" on the setup's success screen and a quiet "Plan with coach" at the end of every goal card's caption, both to `/coach?plan=<goal id>`. The page fills the field with `Plan "<title>" into my week.` and focuses it only for one of the user's own goals; nothing is sent until the person sends it, and any other value leaves the page as it always is.
- [x] "What is sent?" names the routine's keys in words and says that the places of goals are not sent.
- [x] Database (`supabase/migrations/20261214000000_coach_goal_place.sql`, additive): one new security definer function, `app.chat_place_created_events(draft)`. Writing a place into a created event moves its `updated_at` on, and undo only undoes events unchanged since accepting, so the function writes the goal's place through `app.set_event_location` and then remembers the new `updated_at` in the undo data. Only the user's own accepted draft; only created events that are unchanged since accepting, have no location and belong to a goal with a place; the place comes from the goal in the database, never from the caller. Nothing else changes; `main` and the earlier branches work unchanged against it.

## Decisions
- `weeks` is sent for every goal with a routine, also as an empty list (a deadline already passed), because the prompt says "a goal without `weeks` has no routine".
- Done events of the next week are not counted: R31's read ends with the current week, and a session marked done ahead of time is rare.
- `readGoalInputs` reads the routines only when asked (`{ routines: true }`, which `send_message` does). Without the option it returns what it did before spec 43, so spec 41's test that pins "nothing of the routine" for that reader passes unchanged; the reviewer should know that this test now covers only the reader's default, not what `send_message` sends.
- Dragging cannot move a block to another day (spec 22), so a block can reach a never day only when the goal's days changed after the draft was made; that is "out of date", as for accepting.

## Out of scope
Checking the part of the day or the 30 minutes; the coach changing a goal's routine; planning more than two weeks ahead; travel time between two sessions.
